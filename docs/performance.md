## 원인과 변경

기존 firebase.ts는 getAuth와 getFirestore를 함께 호출했습니다. AuthProvider·헤더·인증 페이지가 이 파일을 정적으로 import하므로, 페이지별 지연 로딩이 있어도 Firestore SDK와 관련 의존성이 공통 진입 번들에 포함됐습니다.

firebase.ts에는 웹 앱·Authentication만 남기고, Firestore 초기화를 firestore.ts로 분리했습니다. 데이터 접근 모듈만 firestore.ts를 import하며 동일한 앱 인스턴스를 사용합니다. 기존 페이지별 React.lazy·Suspense·PageLoader 오류 경계·인증 Provider 흐름은 유지했습니다. 별도 vendor 청크 강제 분리나 경고 기준 상향은 적용하지 않았습니다.

변경 전 모듈 구성에서 큰 비중은 React DOM, Firestore, Firestore 의존 re2js, Authentication·WebChannel에 있었습니다. 이 중 인증 화면에 필요하지 않은 Firestore 계열의 로딩 시점을 옮겼습니다. 모듈 renderedLength는 청크의 최종 압축 크기와 다른 값이므로 단순 합산해 전송량으로 사용하지 않습니다.

## 재현 방법

```powershell
npm run analyze:bundle -- current --check
```

스크립트는 현재 vite.config.ts와 로컬 빌드 환경으로 프로덕션 빌드하고 최종 dist 파일을 측정합니다. 결과는 Git 제외 경로 `node_modules/.cache/upday-bundle/current.json`에 저장하며 dist도 현재 빌드로 갱신합니다. 분석 명령은 TypeScript 검사를 대체하지 않으므로 별도로 `npm run build`를 실행합니다.

--check는 로그인·회원가입·비밀번호 재설정 경로의 정적 JS 의존 그래프에 @firebase/firestore 모듈이 있으면 실패합니다. API를 실제 호출하거나 Firebase 데이터를 변경하지 않습니다. 각 경로에 대해 공통 entry와 해당 lazy 페이지의 정적 의존성을 합치고 중복 파일을 제거합니다. CSS 전용으로 최종 출력에서 제거된 JS 청크는 제외합니다.

비교할 때는 변경 전 커밋과 변경 후 커밋 각각의 소스에서 같은 Node·의존성·환경 변수·Vite 설정으로 실행하여 JSON을 별도 보관합니다. snapshot label은 결과 이름일 뿐 소스를 자동으로 전환하지 않습니다.

## 변경 전후 결과

측정일: 2026-10-29. 같은 로컬 환경(Node.js 24.19.0, Vite 8.2.2), 같은 설치 의존성과 환경 변수로 프로덕션 빌드했습니다. 아래 수치는 최종 파일의 실제 바이트 수와 Node gzipSync 기본 설정으로 파일별 압축한 바이트 합계입니다. Vite 콘솔의 gzip 추정값과 측정 조건이 다를 수 있으므로 혼용하지 않습니다.

| 경로/대상 | JS 원본 바이트 전 → 후 | gzip 바이트 전 → 후 | JS 파일 수 전 → 후 |
| --- | --- | --- | --- |
| 공통 entry | 754,457 → 307,941 | 224,964 → 95,061 | 1 → 1 |
| 로그인 | 759,528 → 313,017 | 226,865 → 96,964 | 2 → 2 |
| 회원가입 | 760,684 → 314,173 | 227,107 → 97,209 | 2 → 2 |
| 비밀번호 재설정 | 757,237 → 310,726 | 226,256 → 96,356 | 2 → 2 |
| 대시보드 | 776,568 → 775,929 | 233,565 → 233,121 | 6 → 6 |
| 전체 출력 JS | 865,289 → 864,675 | 264,794 → 264,331 | 18 → 18 |

로그인 경로의 gzip 기준 JS 합계는 약 **57.3% 감소**했습니다. 공개 인증 경로에서 Firestore 모듈이 빠졌고, 데이터 화면인 대시보드에서는 필요한 SDK가 계속 로드됩니다. 총 JS 용량은 크게 바뀌지 않았으며 주된 개선은 불필요한 초기 로드를 데이터 화면 진입 시점으로 미룬 것입니다.

현재 일반 빌드의 최대 청크는 약 448KB이며 기존 500KB 경고는 발생하지 않습니다. 자동 생성 파일명은 useToday 등 최초 공유 모듈 이름을 사용할 수 있으므로 파일명만으로 SDK 포함 여부를 판단하지 않습니다.

## 측정 범위와 한계

- 표의 파일 수는 브라우저 캡처가 아니라 빌드 의존 그래프에서 계산한 JS 요청 예상 수입니다. HTML·CSS·폰트·Firebase API 및 인증 요청은 제외합니다.
- 공개 경로는 비로그인 진입, 대시보드는 인증 완료 후 페이지 로드에 필요한 JS 기준입니다. 네트워크 캐시가 없는 경우를 가정하며 실제 로그인 리다이렉트 비용은 측정하지 않았습니다.
- 정적 import 요청 수가 늘어나지 않은 것은 확인했지만 HTTP waterfall·JS 파싱/실행 시간·FCP·LCP·실제 화면 준비 시간은 측정하지 않았습니다. 번들 감소율을 같은 비율의 화면 로딩 속도 개선으로 해석하지 않습니다.
- 실제 배포 전송량은 서버의 gzip/Brotli 설정·헤더·캐시 정책에 따라 다릅니다. 브라우저·네트워크·CPU와 실제 Firebase 응답의 영향도 별도로 확인해야 합니다.

## 브라우저·배포 확인 절차

1. `npm run build` 후 `npm run preview` 또는 동일한 Preview 배포 환경을 사용합니다.
2. 비로그인 브라우저에서 DevTools Network의 캐시 비활성화, 동일한 네트워크·CPU 제한 조건을 설정합니다. 변경 전후 같은 조건으로 최소 5회씩 cold load하고 중앙값을 비교합니다.
3. /login·/signup·/reset-password의 JS 응답 크기와 요청 순서, Performance의 FCP·LCP 및 화면 준비 시점을 기록합니다. Firebase API 대기 시간과 정적 파일 전송을 구분합니다.
4. 같은 테스트 계정·데이터로 /dashboard 직접 접근 및 로그인 후 이동을 비교합니다. Firestore 청크가 인증 이후 필요할 때 로드되고 기존 대비 순차 요청 지연이 커지지 않는지 waterfall을 확인합니다.
5. Today·Study·Interview·Job 직접 접근·새로고침·CRUD와 마이페이지 이름 변경을 확인합니다. 앱·auth·db가 같은 Firebase 프로젝트를 사용하는지 확인합니다.
6. 테스트 환경에서 페이지 lazy 청크 로드를 차단해 PageLoader의 오류 안내·다시 불러오기 복구를 확인합니다. 실제 계정에 불필요한 변경을 남기지 않습니다.

기존 자동 테스트는 인증·회원가입 재시도·마이페이지·CRUD 및 lazy 페이지 오류 복구를 검증합니다. 브라우저·호스팅 실측 완료를 대신하지 않습니다.
